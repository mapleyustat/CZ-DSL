## 1. 概述与设计目标

### 1.1 定位

CZ-DSL 是面向海岸带复杂系统（Coastal Zone Complex Systems）的领域描述语言。海岸带复杂系统是涉及大气圈、水圈、岩石圈、生物圈和人类活动圈多圈层耦合的开放巨系统，具有高度非线性、多尺度、跨主体等特征。CZ-DSL 旨在为该类系统提供统一的形式化描述框架。

CZ-DSL 同时承担三重语言角色：

| 角色编号 | 语言角色 | 功能定位 | 核心服务对象 |
|:---:|:---|:---|:---|
| R1 | **表述语言**（Representational Language） | 为领域专家提供精确的海岸带系统结构与过程描述手段，支持跨学科语义对齐 | 海洋学家、生态学家、规划师 |
| R2 | **计算语言**（Computational Language） | 衔接数值模拟模型与人工智能模型，提供可执行的模型调用与数据流编排 | 模型开发者、计算科学家 |
| R3 | **业务流程中枢语言**（Business Process Hub Language） | 作为跨政府部门、科研机构和产业主体的业务链路中枢，支撑多主体协同 | 管理决策者、业务协调人员 |

### 1.2 设计目标

| 目标编号 | 设计目标 | 对应语言角色 | 验证标准 |
|:---:|:---|:---:|:---:|
| G1 | 语义完备性：覆盖海岸带复杂系统全部核心业务场景 | R1 | 完备性定理（见形式化验证文档） |
| G2 | 原子不可分性：每个语义单元承载单一语义，复杂场景通过原子组合构建 | R1, R2 | 原子性判定规则 |
| G3 | 时空参照无关性：原生支持任意分辨率、坐标系和参照体系 | R1, R2 | 坐标无关性定理 |
| G4 | 可逆性：数字化描述可逆向还原为原始业务场景信息 | R1, R3 | 可逆性定理 |
| G5 | 可组合性：组件间通过标准化语义接口组合 | R2, R3 | 可组合性定理 |
| G6 | 向后兼容性：原子语法兼容现有 .cz 构造 | R1, R2 | 兼容性映射表 |
| G7 | 行业可推广性：扩展机制保持已有语义不变 | R1, R2, R3 | 扩展同态定理 |

### 1.3 版本演进概述

CZ-DSL 已实现词法分析器（lexer），支持中英双语关键字、物理单位一等公民、几何代数类型（Multivector/Scalar/Vector/Bivector/Trivector）等特性。本版本在既有实现基础上引入七类基础构成分量（原子组件）和四级分层分类体系，将现有分散的 `sphere`/`process`/`model`/`data`/`ai_model`/`digital_twin`/`coastal_database`/`scenario`/`rule`/`infrastructure`/`policy_package`/`spatial_reference_system`/`classification`/`workflow` 构造重新组织为标准化的原子化语义体系。

## 2. 七类基础构成分量

CZ-DSL 的语义体系由七类基础构成分量（Fundamental Component Categories）支撑。每类分量由若干原子组件（Atomic Components）组成，每个原子组件承载单一语义，通过标准化语义接口契约进行组合。

### 2.1 数据接入单元（DataAccessAtom）

#### 2.1.1 语义定义

数据接入单元负责海岸带多源时空数据与专题属性数据的统一描述与接入。其核心设计理念是：在语义底层原生支持任意时空分辨率、任意空间坐标系、任意时空参照体系，消除数据描述层面的信息割裂。

#### 2.1.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `DataSource` | 数据源标识 | 标识一个独立的物理或逻辑数据集 | `identity() -> URI; schema() -> SchemaRef` |
| `CoordinateReference` | 空间坐标系参照 | 描述数据的空间坐标参照体系 | `to_srs(target: SRS) -> Transform; datum() -> Datum` |
| `TemporalReference` | 时间参照 | 描述数据的时间参照体系与时区 | `to_epoch() -> UnixTimestamp; calendar() -> Calendar` |
| `ResolutionSpec` | 分辨率规格 | 描述数据的空间与时间分辨率 | `spatial_res() -> Length; temporal_res() -> Duration` |
| `QualityProfile` | 质量档案 | 描述数据质量等级与质控标记 | `qc_level() -> QCLevel; flags() -> Set<QCFlag>` |
| `UncertaintyModel` | 不确定性模型 | 描述数据不确定性的数学模型 | `distribution() -> Distribution; ci(level: Real) -> Range` |
| `AccessEndpoint` | 访问端点 | 描述数据访问的协议与地址 | `protocol() -> Protocol; endpoint() -> URI` |

#### 2.1.3 语法形式

```
data_source <标识符> {
    source: DataSource { ... },
    coordinate_ref: CoordinateReference { ... },
    temporal_ref: TemporalReference { ... },
    resolution: ResolutionSpec { ... },
    quality: QualityProfile { ... },
    uncertainty: UncertaintyModel { ... },
    endpoint: AccessEndpoint { ... }
}
```

#### 2.1.4 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `coastal_database` | `DataSource` + `CoordinateReference` + `TemporalReference` + `ResolutionSpec` | 数据库整体拆解为数据接入单元 |
| `dataset` | `DataSource` + `ResolutionSpec` + `QualityProfile` + `UncertaintyModel` | 数据集原子化 |
| `layer` | `DataSource` + `CoordinateReference` | 图层映射为带坐标参照的数据源 |
| `spatial_reference_system` | `CoordinateReference` + `TemporalReference` | SRS 拆分为空间与时间参照原子 |

### 2.2 模型适配单元（ModelAdapterAtom）

#### 2.2.1 语义定义

模型适配单元负责衔接数值模拟模型（如 ROMS、FVCOM、SWAN）、机器学习模型（如神经网络预测器）和业务流程模型（如工作流引擎），提供统一的模型接口契约与调用绑定机制。

#### 2.2.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `ModelInterface` | 模型接口 | 描述模型的输入/输出接口签名 | `inputs() -> [TypeExpr]; outputs() -> [TypeExpr]` |
| `ModelCapability` | 模型能力 | 描述模型可提供的计算能力类型 | `capabilities() -> Set<Capability>; domain() -> Domain` |
| `ModelIOContract` | 输入输出契约 | 约束模型输入输出的类型与单位 | `validate(input: Map) -> Result; output_schema() -> Schema` |
| `ModelVersion` | 模型版本 | 标识模型的具体版本与依赖 | `version() -> SemVer; dependencies() -> [ModelRef]` |
| `ModelDeployment` | 模型部署 | 描述模型的运行环境与资源需求 | `runtime() -> RuntimeSpec; resources() -> ResourceSpec` |
| `ModelInvokeBinding` | 调用绑定 | 将模型绑定到特定场景与数据 | `bind(data: DataAccessAtom, scenario: ScenarioRef) -> BoundModel` |

#### 2.2.3 语法形式

```
model_adapter <标识符> {
    interface: ModelInterface { ... },
    capability: ModelCapability { ... },
    io_contract: ModelIOContract { ... },
    version: ModelVersion { ... },
    deployment: ModelDeployment { ... },
    invoke_binding: ModelInvokeBinding { ... }
}
```

#### 2.2.4 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `model` | `ModelInterface` + `ModelCapability` + `ModelIOContract` | 数值模型拆解为接口、能力与契约 |
| `ai_model` | `ModelInterface` + `ModelCapability` + `ModelVersion` | AI 模型增加版本与能力描述 |
| `process` | `ModelInterface` + `ModelIOContract` | 过程映射为接口与契约原子 |
| `workflow` | `ModelInvokeBinding` + `ModelDeployment` | 工作流映射为调用绑定与部署 |
| `recommend_model()` | `ModelCapability` + `ModelInvokeBinding` | 模型推荐映射为能力匹配与绑定 |

### 2.3 跨主体关联引擎（CrossSubjectLinkEngine）

#### 2.3.1 语义定义

跨主体关联引擎负责建立跨政府部门（如自然资源部、生态环境部、交通运输部）、科研机构（如海洋研究所、大学实验室）和产业主体（如港口集团、渔业企业）之间的语义关联。引入 SEDRIS EDCS（Environmental Data Coding Specification）和 CMECS（Coastal and Marine Ecological Classification Standard）作为分类锚点，确保跨主体语义对齐。

#### 2.3.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `Subject` | 行为主体 | 标识一个参与海岸带管理的组织或个体 | `id() -> SubjectID; type() -> SubjectType` |
| `Role` | 角色 | 描述主体在业务链路中的角色 | `permissions() -> Set<Permission>; scope() -> Scope` |
| `Jurisdiction` | 管辖范围 | 描述主体的行政与空间管辖边界 | `boundary() -> Polygon; level() -> AdminLevel` |
| `SemanticLink` | 语义关联 | 建立主体间的语义关联关系 | `source() -> SubjectRef; target() -> SubjectRef; type() -> LinkType` |
| `Provenance` | 溯源信息 | 记录数据与决策的来源链 | `origin() -> SubjectRef; timestamp() -> DateTime; chain() -> [Provenance]` |
| `Authorization` | 授权 | 描述主体间的数据与操作授权 | `granted_by() -> SubjectRef; granted_to() -> SubjectRef; scope() -> AuthScope` |
| `Responsibility` | 责任 | 描述主体在特定业务中的职责 | `duty() -> Duty; accountable_to() -> SubjectRef` |

#### 2.3.3 分类锚点

跨主体关联引擎以 SEDRIS EDCS 与 CMECS 作为标准分类锚点：

- **EDCS 锚点**：通过 `ECC_*` 编码体系（Environmental Classification Codes）对环境对象进行统一分类，如 `ECC_TYPHOON`、`ECC_SALT_MARSH`、`ECC_RIVER_MOUTH`。
- **CMECS 锚点**：通过 CMECS 四组分（Biotic、Geoform、Substrate、WaterColumn）对海岸带生态单元进行标准化分类，对应现有 `cmecs.rs` 中的 `CmecsComponent` 枚举。

#### 2.3.4 语法形式

```
cross_subject_link <标识符> {
    subject: Subject { ... },
    role: Role { ... },
    jurisdiction: Jurisdiction { ... },
    semantic_links: [SemanticLink { ... }],
    provenance: Provenance { ... },
    authorization: Authorization { ... },
    responsibility: Responsibility { ... }
}
```

#### 2.3.5 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `classification` (EDCS) | `Subject` + `SemanticLink` | EDCS 分类映射为语义关联锚点 |
| `classification` (CMECS) | `SemanticLink` + `Jurisdiction` | CMECS 分类映射为管辖关联 |

### 2.4 大模型调度接口（LLMDispatchInterface）

#### 2.4.1 语义定义

大模型调度接口负责对接通用人工智能（AGI）逻辑推理能力与地理大模型空间认知能力，提供任务定义、提示契约、输出绑定、接地约束和幻觉防护等原子组件。

#### 2.4.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `LLMTask` | 任务定义 | 定义一个面向大模型的推理或认知任务 | `input() -> PromptData; expected() -> OutputSchema` |
| `PromptContract` | 提示契约 | 约束提示词的结构、变量与格式 | `template() -> PromptTemplate; variables() -> Map<Var, Type>` |
| `SpatialCognitionCall` | 空间认知调用 | 调用地理大模型进行空间推理 | `spatial_query() -> SpatialQuery; model() -> GeoLLMRef` |
| `LogicInferenceCall` | 逻辑推理调用 | 调用通用大模型进行逻辑推理 | `premises() -> [Proposition]; query() -> InferenceQuery` |
| `LLMOutputBinding` | 输出绑定 | 将大模型输出绑定到领域语义 | `parse(raw: Text) -> DomainValue; schema() -> OutputSchema` |
| `GroundingConstraint` | 接地约束 | 约束大模型输出必须基于事实数据 | `grounding_source() -> DataAccessAtom; tolerance() -> Real` |
| `HallucinationGuard` | 幻觉防护 | 检测并阻止大模型幻觉输出 | `validate(output: DomainValue) -> GuardResult; threshold() -> Real` |

#### 2.4.3 语法形式

```
llm_dispatch <标识符> {
    task: LLMTask { ... },
    prompt: PromptContract { ... },
    spatial_cognition: SpatialCognitionCall { ... },
    logic_inference: LogicInferenceCall { ... },
    output_binding: LLMOutputBinding { ... },
    grounding: GroundingConstraint { ... },
    hallucination_guard: HallucinationGuard { ... }
}
```

#### 2.4.4 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `ai_model` (推理部分) | `LLMTask` + `PromptContract` + `LLMOutputBinding` | AI 模型推理映射为大模型调度 |
| `rule` | `LogicInferenceCall` + `GroundingConstraint` | 规则推理映射为逻辑调用与接地约束 |

### 2.5 颗粒度划分引擎（GranularityPartitionEngine）

#### 2.5.1 语义定义

颗粒度划分引擎负责按照国土空间规划、生态保护修复、灾害应急处置等业务特征，对海岸带系统进行多颗粒度层级划分，支持聚合与解聚操作。

#### 2.5.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `GranularityLevel` | 颗粒度层级 | 定义一个离散的颗粒度等级 | `level() -> UInt; scale_range() -> (Length, Length)` |
| `PartitionRule` | 划分规则 | 定义从上级到下级的划分准则 | `apply(parent: Unit) -> [Unit]; criterion() -> Criterion` |
| `AggregationOperator` | 聚合算子 | 定义从下级到上级的聚合操作 | `aggregate(children: [Unit]) -> Unit; method() -> AggMethod` |
| `DisaggregationOperator` | 解聚算子 | 定义从上级到下级的解聚操作 | `disaggregate(parent: Unit) -> [Unit]; method() -> DisaggMethod` |
| `BoundaryRule` | 边界规则 | 定义颗粒度单元的边界确定准则 | `resolve(conflict: Boundary) -> Boundary; priority() -> UInt` |

#### 2.5.3 语法形式

```
granularity <标识符> {
    levels: [GranularityLevel { ... }],
    partition_rules: [PartitionRule { ... }],
    aggregation: AggregationOperator { ... },
    disaggregation: DisaggregationOperator { ... },
    boundary_rules: [BoundaryRule { ... }]
}
```

#### 2.5.4 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `scale` | `GranularityLevel` + `PartitionRule` | 尺度声明映射为颗粒度层级与划分规则 |
| `model.coupling` (Upscaling/Downscaling) | `AggregationOperator` + `DisaggregationOperator` | 尺度间耦合映射为聚合/解聚算子 |

### 2.6 分层分类管理器（LayeredClassificationManager）

#### 2.6.1 语义定义

分层分类管理器构建"全域—海岸带单元—核心斑块—基础要素"四级分层分类体系。每一级具有明确的定义、判别准则、编码规则，并与 CMECS/EDCS 标准对齐。

#### 2.6.2 四级体系定义

**第一级：全域（WholeDomain）**

- 定义：覆盖完整海岸带研究区域的最大空间范围单元。
- 判别准则：空间范围覆盖整个研究区域边界，不与同级单元重叠。
- 编码规则：`CZ.WD.<区域代码>.<序号>`
- CMECS/EDCS 对齐：对应 EDCS 顶层环境分类（如 `EDCS_ESTUARY`、`EDCS_COASTAL_ZONE`）。
- 编码示例：`CZ.WD.ECS.01`（东海陆架全域单元01）

**第二级：海岸带单元（CoastalCell）**

- 定义：全域内按地貌—水动力—生态特征划分的次级功能单元。
- 判别准则：具有相对独立的水动力循环或生态过程边界，面积在 10²—10⁴ km² 量级。
- 编码规则：`CZ.CC.<地貌代码>-<生态代码>-<序号>`
- CMECS/EDCS 对齐：对应 CMECS Geoform 组分层级 + EDCS 子分类。
- 编码示例：`CZ.CC.YZ-E-01`（长江口-河口生态-单元01）

**第三级：核心斑块（CorePatch）**

- 定义：海岸带单元内具有特定生态功能或人类活动特征的同质性地块。
- 判别准则：斑块内部具有一致的地表覆盖类型或土地利用类型，面积在 10⁻¹—10² km² 量级。
- 编码规则：`CZ.CP.<斑块类型代码>-<序号>`
- CMECS/EDCS 对齐：对应 CMECS Biotic/Substrate 组分层级。
- 编码示例：`CZ.CP.WTL-01`（湿地斑块-01）

**第四级：基础要素（BaseElement）**

- 定义：核心斑块内不可进一步细分的基础观测或管理要素。
- 判别准则：承载单一物理量或单一管理属性的原子要素，空间尺度 < 10⁻¹ km²。
- 编码规则：`CZ.BE.<要素类型代码>-<子类型代码>-<序号>`
- CMECS/EDCS 对齐：对应 CMECS 最细分类单元 + EDCS 属性编码。
- 编码示例：`CZ.BE.SED-MUD-01`（沉积物-泥质-要素01）

#### 2.6.3 覆盖范围

分层分类管理器必须覆盖以下三大类要素：

| 类别 | 子类 | 对应层级 | CMECS/EDCS 对齐 |
|:---|:---|:---:|:---|
| **自然要素** | 大气（气温、气压、风场、降水） | WD—CC | EDCS_Atmosphere |
| | 水文（海表温度、盐度、波浪、潮汐、洋流） | WD—CC—CP | CMECS_WaterColumn + EDCS_Hydro |
| | 地形（水深、海岸线、高程） | WD—CC | CMECS_Geoform + EDCS_Topography |
| | 地质（沉积物类型、底质组成） | CC—CP—BE | CMECS_Substrate + EDCS_Geology |
| **人类活动** | 渔业生产（渔区、捕捞量、养殖区） | CC—CP | EDCS_Fishery |
| | 港口运营（码头、航道、锚地） | CC—CP | EDCS_Port |
| | 城镇建设（建设用地、防护工程） | CP—BE | EDCS_Urban |
| **生态过程** | 碳循环（碳汇、碳通量、碳储量） | WD—CC—CP | EDCS_Carbon |
| | 生物迁徙（鸟类迁徙通道、鱼类洄游路线） | WD—CC | EDCS_Migration |
| | 污染扩散（污染物浓度、扩散路径） | CC—CP—BE | EDCS_Pollution |

#### 2.6.4 语法形式

```
classification_layer <标识符> {
    level: WholeDomain | CoastalCell | CorePatch | BaseElement,
    code: <编码字符串>,
    parent: <上级编码引用>,
    criteria: <判别准则表达式>,
    cmecs_alignment: <CMECS分类引用>,
    edcs_alignment: <EDCS分类引用>,
    elements: [ <要素列表> ]
}
```

#### 2.6.5 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `classification` | `classification_layer` (多级) | 分类声明映射为分层分类层级 |
| `layer` (in coastal_database) | `classification_layer` (CorePatch级) | 数据库图层映射为核心斑块级分类 |

### 2.7 数字化映射模块（DigitalTwinMapping）

#### 2.7.1 语义定义

数字化映射模块负责物理资产与数字副本之间的映射关系管理，包括数据同化绑定、仿真绑定、反馈控制和状态变量管理等。

#### 2.7.2 原子组件清单

| 原子组件 | 语义角色 | 不可分语义 | 接口契约 |
|:---|:---|:---|:---|
| `PhysicalAsset` | 物理资产 | 标识一个被映射的物理实体 | `id() -> AssetID; geometry() -> Geometry` |
| `DigitalReplica` | 数字副本 | 描述物理资产的数字模型 | `model() -> ModelRef; fidelity() -> FidelityLevel` |
| `AssimilationBinding` | 同化绑定 | 将观测数据绑定到数字模型的状态更新 | `method() -> AssimilationMethod; frequency() -> Duration` |
| `SimulationBinding` | 仿真绑定 | 将数字模型绑定到仿真执行 | `engine() -> SimEngine; horizon() -> Duration` |
| `FeedbackControl` | 反馈控制 | 描述从数字模型到物理资产的反馈控制链 | `actuators() -> [Actuator]; policy() -> ControlPolicy` |
| `StateVariable` | 状态变量 | 描述数字孪生系统的状态量 | `name() -> Identifier; type() -> TypeExpr; unit() -> Unit` |
| `ObservationStream` | 观测流 | 描述实时观测数据流 | `source() -> DataAccessAtom; rate() -> Frequency` |

#### 2.7.3 语法形式

```
digital_twin_mapping <标识符> {
    physical_asset: PhysicalAsset { ... },
    digital_replica: DigitalReplica { ... },
    assimilation: AssimilationBinding { ... },
    simulation: SimulationBinding { ... },
    feedback_control: FeedbackControl { ... },
    state_variables: [StateVariable { ... }],
    observation_streams: [ObservationStream { ... }]
}
```

#### 2.7.4 与现有 .cz 构造的映射

| 现有构造 | 原子组合 | 映射说明 |
|:---|:---|:---|
| `digital_twin` | `PhysicalAsset` + `DigitalReplica` + `AssimilationBinding` + `SimulationBinding` + `FeedbackControl` | 数字孪生构造原子化拆解 |
| `digital_twin.assimilation` | `AssimilationBinding` + `StateVariable` + `ObservationStream` | 同化模块映射 |
| `digital_twin.simulation` | `SimulationBinding` | 仿真模块映射 |
| `digital_twin.control` | `FeedbackControl` | 控制模块映射 |

### 4.4 共享语法规则

```ebnf

(* 常量/变量声明 *)

constraint_body = quantified_expr | expression ;
quantified_expr = ("∀" | "forall" | "∃" | "exists") identifier ":" type_expr "=>" expression ;

parameter_member = identifier ":" type_expr [ "=" expression ] "," ;
variable_member = identifier ":" type_expr [ "=" expression ] "," ;
equation_member = identifier ":" expression "," ;

(* 参数列表 *)
parameter_list = parameter { "," parameter } ;
parameter = identifier ":" type_expr [ "=" expression ] ;

(* 类型表达式 *)
type_expr = basic_type | generic_type | function_type | tuple_type | array_type
          | field_type | uncertain_type | unit_type ;
basic_type = "Real" | "Integer" | "Complex" | "Boolean" | "String"
           | "Vector3D" | "Point2D" | "Point3D" | "GeoPoint"

           | expression "..=" expression
           | ".." expression

generic_params = "<" generic_param { "," generic_param } ">" ;
generic_param = identifier [ ":" type_expr { "+" type_expr } ] ;

(* 标识符与字面量 *)
identifier = ascii_identifier | unicode_identifier ;
ascii_identifier = ( letter | "_" ) { letter | digit | "_" } ;
unicode_identifier = xid_start { xid_continue } ;
identifier_list = identifier { "," identifier } ;
integer_literal = digit { digit } ;
float_literal = digit { digit } "." digit { digit } [ ("e" | "E") [ "+" | "-" ] digit { digit } ] ;
string_literal = "\"" { string_char } "\"" ;
expression_list = expression { "," expression } ;

(* 语句与表达式（与复合构造保持一致） *)
statement = expression_stmt | assignment_stmt | if_stmt | for_stmt | while_stmt
          | match_stmt | loop_stmt | break_stmt | continue_stmt | return_stmt | block_stmt ;
block_stmt = "{" { statement } "}" ;

expression = logical_or_expr ;
logical_or_expr = logical_and_expr { "||" logical_and_expr } ;
logical_and_expr = equality_expr { "&&" equality_expr } ;
equality_expr = relational_expr { ( "==" | "!=" | "≠" ) relational_expr } ;
relational_expr = additive_expr { ( "<" | "<=" | ">" | ">=" | "≤" | "≥" ) additive_expr } ;
additive_expr = multiplicative_expr { ( "+" | "-" ) multiplicative_expr } ;
multiplicative_expr = power_expr { ( "*" | "/" | "%" ) power_expr } ;
power_expr = unary_expr [ "**" power_expr ] ;
unary_expr = ( "+" | "-" | "!" | "∇" | "∂" ) unary_expr | postfix_expr ;
postfix_expr = primary_expr { "." identifier [ "(" [ expression_list ] ")" ]
                            | "[" expression "]"
                            | "(" [ expression_list ] ")" } ;
primary_expr = literal | identifier | "(" expression ")" | "[" [ expression_list ] "]"
             | "(" expression_list ")" | lambda_expr ;
lambda_expr = "|" [ parameter_list ] "|" ( expression | block_stmt ) ;
literal = integer_literal | float_literal | string_literal | "true" | "false" | "()" ;

(* 字符类 *)
letter = "a" .. "z" | "A" .. "Z" ;
digit = "0" .. "9" ;
xid_start = (* Unicode XID_Start *) ;
xid_continue = (* Unicode XID_Continue *) ;
string_char = (* any char except " and \ *) | escape_sequence ;
escape_sequence = "\\" ( "n" | "t" | "r" | "\\" | "\"" | "'" | "0" ) ;
```

### 6.4 兼容性保证机制

原子构造通过以下机制保证与复合构造共存：

1. **语法兼容**：所有复合关键字在原子构造中保留并可直接解析。新增原子构造关键字不影响 复合构造的语法分析。
2. **语义升级**：复合构造在 原子语义模型中自动映射为对应的原子组合，无需修改源文件。
3. **渐进迁移**：复合构造文件可逐步引入 原子构造，新旧构造可混合使用。
4. **工具链兼容**：原子词法分析器向后兼容既有词法分析器的全部 Token 类型。
