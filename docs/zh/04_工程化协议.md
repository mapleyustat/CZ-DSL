## 1. 协议概述与版本治理

### 1.1 设计目标

CZ-DSL 1.0 是海岸带领域描述语言的第二代工程化协议，在 v1 文本语法（`.cz` 文件）基础上
新增 XML 与 JSON 两种序列化形式，形成**三种等价表示**。协议设计参考 KML、CityGML、GML
的 Schema 设计范式，并在分类体系上对齐 CMECS（Coastal and Marine Ecological
Classification Standard）与 EDCS（Environmental Data Coding Specification），在坐标
参考上兼容 SEDRIS SRM（Spatial Reference Model）。

本版本的核心架构由**七大组件**构成：

| 编号 | 组件名 | 职责 |
|------|--------|------|
| 1 | DataAccess | 数据源、坐标参考、时间参考、分辨率、质量、不确定性、访问端点 |
| 2 | ModelAdapter | 模型接口、能力、IO 契约、版本、部署、调用绑定 |
| 3 | CrossSubjectLink | 主体、角色、管辖权、语义链接、溯源、授权、责任 |
| 4 | LLMDispatch | LLM 任务、提示契约、空间认知调用、逻辑推理调用、输出绑定、接地约束、幻觉防护 |
| 5 | GranularityPartition | 粒度层级、分区规则、聚合/解聚算子、边界规则 |
| 6 | LayeredClassification | 四级分类层（WholeDomain / CoastalCell / CorePatch / BaseElement） |
| 7 | DigitalTwinMapping | 物理资产、数字副本、同化绑定、仿真绑定、反馈控制、状态变量、观测流 |

每个组件由若干**原子（Atom）**组成，原子是协议的最小可插拔单元。

### 1.2 版本治理

- **当前版本**: 1.0.0（语义化版本 MAJOR.MINOR.PATCH）
- **向后兼容**: 完全兼容既有复合构造的 `.cz` 文本语法。既有场景文件可通过编译器前端解析
  后映射到 七组件架构，原有 `sphere`、`process`、`model`、`data`、`ai_model`、
  `digital_twin`、`coastal_database`、`scenario`、`rule`、`infrastructure`、
  `policy_package`、`spatial_reference_system`、`classification`、`workflow` 等顶级
  关键字分别归入对应组件组。
- **命名空间**: XML 命名空间为 `http://cz-dsl.org/schema/1.0`，前缀 `cz`。
- **Schema 文件**:
  - XSD: `cz-dsl.xsd`
  - JSON Schema: `cz-dsl.schema.json`（Draft 2020-12）

### 1.3 复合构造到原子构造的关键字映射

| 复合关键字 | 目标原子组件 | 说明 |
|-----------|------------|------|
| `spatial_reference_system` | DataAccess / CoordinateReference | 坐标参考原子化 |
| `coastal_database` | DataAccess / DataSource | 数据库即数据源 |
| `data` | DataAccess / DataSource | 数据声明映射为数据源原子 |
| `model` | ModelAdapter / ModelInterface | 模型声明映射为模型接口原子 |
| `ai_model` | ModelAdapter / ModelInterface + LLMDispatch | AI 模型跨组件映射 |
| `process` | ModelAdapter / ModelIOContract | 过程的输入输出映射为 IO 契约 |
| `digital_twin` | DigitalTwinMapping | 直接映射 |
| `scenario` | CZScenario 根元素 | 场景成为根容器 |
| `rule` | CrossSubjectLink / Responsibility | 规则映射为责任约束 |
| `infrastructure` | DigitalTwinMapping / PhysicalAsset | 基础设施映射为物理资产 |
| `policy_package` | CrossSubjectLink / Jurisdiction | 政策包映射为管辖权与责任 |
| `classification` | LayeredClassification / ClassificationLayer | 分类映射为四级分类层 |
| `workflow` | GranularityPartition / PartitionRule | 工作流映射为分区规则 |

## 2. 语法规则：三种等价表示

### 2.1 文本语法（EBNF 摘要）

以下为 文本语法的 EBNF 摘要，完整语法规范参见 `01_语言规范.md`。

```ebnf
scenario       ::= "scenario" identifier "{" scenario_body "}"
scenario_body  ::= metadata spatial_ref temporal_ref granularity component_group*
metadata       ::= "metadata" "{" "title" ":" string ("description" ":" string)? "}"
spatial_ref    ::= "spatial_reference" "{" crs_body "}"
temporal_ref   ::= "temporal_reference" "{" temporal_body "}"
granularity    ::= "granularity" ":" level
level          ::= "WholeDomain" | "CoastalCell" | "CorePatch" | "BaseElement"
component_group::= data_access | model_adapter | cross_subject | llm_dispatch
                | granularity_partition | layered_classification | digital_twin
atom           ::= atom_name identifier "{" atom_body "}"
atom_body      ::= (key ":" value (unit)?) ("," key ":" value)*
```

### 2.2 XML 序列化

XML 序列化遵循 W3C XML Schema 定义（`cz-dsl.xsd`），根元素为 `cz:CZScenario`。

### 2.3 JSON 序列化

JSON 序列化遵循 JSON Schema Draft 2020-12（`cz-dsl.schema.json`），根对象为
`CZScenario`。

### 2.4 三种表示对照表

| 概念 | .cz 文本 | XML | JSON |
|------|---------|-----|------|
| 场景根 | `scenario X { }` | `<cz:CZScenario id="X">` | `{"id":"X",...}` |
| 元数据 | `metadata { title: "T" }` | `<metadata><Title>T</Title></metadata>` | `"metadata":{"title":"T"}` |
| 坐标参考 | `spatial_reference { epsg: 32651 }` | `<spatialReference><EPSG>32651</EPSG></spatialReference>` | `"spatialReference":{"epsg":32651}` |
| 时间参考 | `temporal_reference { epoch: "2025-01-01" }` | `<temporalReference><Epoch>2025-01-01</Epoch></temporalReference>` | `"temporalReference":{"epoch":"2025-01-01"}` |
| 粒度 | `granularity: CoastalCell` | `<granularity><Level>CoastalCell</Level></granularity>` | `"granularity":{"level":"CoastalCell"}` |
| 数据源原子 | `DataSource ds1 { protocol: OPeNDAP }` | `<DataSource id="ds1"><Protocol>OPeNDAP</Protocol></DataSource>` | `{"id":"ds1","protocol":"OPeNDAP"}` |
| 模型接口原子 | `ModelInterface m1 { modelName: FVCOM }` | `<ModelInterface id="m1"><ModelName>FVCOM</ModelName></ModelInterface>` | `{"id":"m1","modelName":"FVCOM"}` |
| 主体原子 | `Subject s1 { subjectName: "水利局" }` | `<Subject id="s1"><SubjectName>水利局</SubjectName></Subject>` | `{"id":"s1","subjectName":"水利局"}` |
| LLM 任务 | `LLMTask t1 { taskType: "SLR_projection" }` | `<LLMTask id="t1"><TaskType>SLR_projection</TaskType></LLMTask>` | `{"id":"t1","taskType":"SLR_projection"}` |
| 分类层 | `ClassificationLayer { level: CoastalCell, code: "CZ.CC.HZB-01" }` | `<ClassificationLayer id="..."><Level>CoastalCell</Level><Code>CZ.CC.HZB-01</Code></ClassificationLayer>` | `{"id":"...","level":"CoastalCell","code":"CZ.CC.HZB-01"}` |
| 物理资产 | `PhysicalAsset a1 { assetType: Seawall }` | `<PhysicalAsset id="a1"><AssetType>Seawall</AssetType></PhysicalAsset>` | `{"id":"a1","assetType":"Seawall"}` |
| 扩展槽 | `x-blue-carbon { ... }` | `<ExtensionSlot><bc:BlueCarbon .../></ExtensionSlot>` | `"x-blue-carbon": {...}` |

## 3. 语义 Schema 约束

### 3.1 Schema 文件引用

- XML 约束: `cz-dsl.xsd`（W3C XML Schema）
- JSON 约束: `cz-dsl.schema.json`（JSON Schema Draft 2020-12）

### 3.2 基数约束

| 组件 | 原子 | 最少 | 最多 | 说明 |
|------|------|------|------|------|
| DataAccess | DataSource | 0 | 无限 | 至少推荐 1 个数据源 |
| DataAccess | CoordinateReference | 0 | 无限 | 场景级 CRS 在根元素定义 |
| ModelAdapter | ModelInterface | 0 | 无限 | 每个模型实例一个 |
| ModelAdapter | ModelIOContract | 0 | 无限 | 与 ModelInterface 配对 |
| CrossSubjectLink | Authorization | 0 | 无限 | 跨主体授权必须校验 |
| LLMDispatch | GroundingConstraint | 0 | 无限 | 推荐 ≥1 以防幻觉 |
| GranularityPartition | AggregationOperator | 0 | 无限 | 聚合算子与分区规则配合 |
| LayeredClassification | ClassificationLayer | 0 | 无限 | 四级层次各至少推荐 1 层 |
| DigitalTwinMapping | PhysicalAsset | 0 | 无限 | 与 DigitalReplica 配对 |

### 3.3 单位一致性校验

`UnitType`（XSD）/ `Unit`（JSON Schema）携带七个 SI 量纲属性
（`siLength`、`siMass`、`siTime`、`siCurrent`、`siTemperature`、`siAmount`、
`siLuminosity`）。运行时校验规则：

1. **模型 IO 契约校验**: `ModelIOContract` 的输入单位与 `ModelInterface` 声明的
   期望单位进行量纲匹配，量纲不一致即拒绝调用。
2. **数据源分辨率校验**: `ResolutionSpec` 的 `spatialResolution` 必须具有
   `siLength=1`，`temporalResolution` 必须具有 `siTime=1`。
3. **状态变量校验**: `StateVariable` 的 `unit` 必须与同化绑定
   `AssimilationBinding` 中观测数据的单位一致。

示例（JSON）:
```json
{
  "variableName": "sea_surface_height",
  "unit": { "value": "meter", "siLength": 1 }
}
```

### 3.4 坐标一致性校验

`CoordinateReferenceType`（XSD）/ `CoordinateReference`（JSON Schema）支持通过
EPSG 代码、WKT 定义及动态参数描述任意 CRS。

校验规则：
1. 场景根 `spatialReference` 定义全局 CRS，所有组件内 `CoordinateReference` 原子
   若声明不同 CRS，必须提供到全局 CRS 的转换路径。
2. `srmMapping` 属性可引用 SEDRIS SRM 坐标系标识（如
   `SRM_GEODETIC_WGS_1984`），运行时通过 SRM 转换器验证一致性。
3. 动态参数 `epoch`、`tidalDatum`、`geoidModel` 必须在涉及潮汐基准的场景中
   明确声明，否则警告。

### 3.5 四级分类编码校验

`ClassificationCodeType` 强制编码模式为：

```
CZ.(WD|CC|CP|BE).[A-Z0-9-]+
```

| 前缀 | 层级 | 含义 |
|------|------|------|
| `CZ.WD.*` | WholeDomain | 全域级 |
| `CZ.CC.*` | CoastalCell | 海岸单元级 |
| `CZ.CP.*` | CorePatch | 核心斑块级 |
| `CZ.BE.*` | BaseElement | 基础要素级 |

校验规则：
1. `ClassificationLayer` 的 `level` 枚举值与 `code` 前缀必须一致（如
   `level=CoastalCell` 时 `code` 必须以 `CZ.CC.` 开头）。
2. `parentCode` 若存在，必须指向比当前层级高一级的分类编码。
3. `cmecsRef` 和 `edcsRef` 可选，用于交叉引用 CMECS/EDCS 分类代码。

### 3.6 跨主体授权校验

`CrossSubjectLink` 组件中的 `Authorization` 原子声明 `(principal, action, resource)`
三元组。校验规则：

1. 当 `LLMDispatch` 中的 LLM 调用涉及数据访问时，必须存在对应的
   `Authorization` 授权条目。
2. `Responsibility` 的 `assignee` 必须引用已声明的 `Subject`。
3. `Jurisdiction` 的 `scope` 必须与场景的空间范围兼容。

## 4. 数据交互接口

### 4.1 接口总览

协议定义四类核心接口：

| 接口 | 方法 | 用途 |
|------|------|------|
| Atom 注册 | `registerAtom` | 注册新原子类型到运行时 |
| 场景装载/导出 | `loadScenario` / `exportScenario` | 装载或导出完整场景 |
| 模型绑定调用 | `invokeModel` | 调用已绑定的数值/AI 模型 |
| LLM 调度 | `dispatchLLM` | 调度 LLM 执行推理任务 |

### 4.2 Atom 注册接口 (registerAtom)

**接口签名 (IDL)**:
```
interface AtomRegistry {
  RegisterAtomResponse registerAtom(
    AtomDefinition definition,
    ExtensionRegistry registry
  ) raises(AtomConflictError, SchemaValidationError);
}

struct AtomDefinition {
  string atomName;
  string extendsAtom;     // 继承的父原子，必须是 AtomType 子类
  string xsdFragment;     // XSD 扩展片段（可选）
  string jsonSchemaFragment; // JSON Schema 扩展片段（可选）
  string czGrammarRule;   // .cz 文本语法扩展规则（可选）
};
```

**请求示例 (JSON)**:
```json
{
  "method": "registerAtom",
  "params": {
    "atomName": "BlueCarbonAccountingAtom",
    "extendsAtom": "cz:AtomType",
    "jsonSchemaFragment": "{\"properties\":{\"carbonFlux\":{\"type\":\"number\"}}}"
  }
}
```

**响应示例 (JSON)**:
```json
{
  "status": "ok",
  "atomId": "urn:cz-dsl:atom:BlueCarbonAccountingAtom",
  "version": "1.0.0",
  "registeredAt": "2026-08-14T10:00:00Z"
}
```

## 5. 无侵入式扩展机制（核心）

### 5.1 双重扩展机制

CZ-DSL 1.0 提供两层无侵入式扩展机制，确保核心 schema 永不需修改即可支持新需求：

#### 机制一：AtomType 抽象基类 + 继承

所有原子类型继承自抽象基类 `AtomType`，该基类提供四个通用属性：

| 属性 | 类型 | 说明 |
|------|------|------|
| `id` | `xs:ID` / `string` | 原子唯一标识（必需） |
| `version` | `string` | 原子版本 |
| `extends` | `string` | 继承的父原子标识 |
| `source` | `string` | 数据/模型来源 |

新原子通过 `extends` 属性继承已有原子，无需修改核心 schema 中的类型定义。

XSD 片段:
```xml
<xs:complexType name="AtomType" abstract="true">
  <xs:sequence>
    <xs:element name="ExtensionSlot" type="cz:ExtensionSlotType"
                minOccurs="0" maxOccurs="unbounded"/>
  </xs:sequence>
  <xs:attribute name="id" type="xs:ID" use="required"/>
  <xs:attribute name="version" type="xs:string" default="1.0.0"/>
  <xs:attribute name="extends" type="xs:string" use="optional"/>
  <xs:attribute name="source" type="xs:string" use="optional"/>
  <xs:anyAttribute namespace="##any" processContents="lax"/>
</xs:complexType>
```

JSON Schema 片段:
```json
{
  "Atom": {
    "type": "object",
    "required": ["id"],
    "properties": {
      "id": { "type": "string" },
      "version": { "type": "string", "default": "1.0.0" },
      "extends": { "type": "string" },
      "source": { "type": "string" }
    },
    "patternProperties": { "^x-": {} }
  }
}
```

#### 机制二：ExtensionSlot（x- 前缀 / xs:any lax）

`ExtensionSlot` 提供通配扩展点：

- **XML**: 使用 `xs:any namespace="##any" processContents="lax"` 和
  `xs:anyAttribute namespace="##any" processContents="lax"`，允许插入任意命名空间的
  元素和属性，校验器对未知内容采取宽松策略（有 schema 则校验，无则放行）。
- **JSON**: 使用 `patternProperties: { "^x-": {} }`，允许以 `x-` 前缀开头的任意属性。

### 5.2 扩展注册表 (Extension Registry) 规范

扩展注册表是一个全局目录，记录所有已注册的扩展原子、数据类型和模型接口。

**注册表条目结构 (JSON)**:
```json
{
  "extensionId": "urn:cz-dsl:ext:blue-carbon:1.0.0",
  "name": "BlueCarbonAccountingAtom",
  "extends": "cz:AtomType",
  "component": "DigitalTwinMapping",
  "version": "1.0.0",
  "status": "active",
  "schema": {
    "xsd": "extensions/blue-carbon.xsd",
    "json": "extensions/blue-carbon.schema.json"
  },
  "czGrammar": "extensions/blue-carbon.grammar.ebnf"
}
```

**注册表生命周期**:
1. **提交 (Propose)**: 扩展开发者提交注册表条目。
2. **审查 (Review)**: 核心团队审查兼容性与命名规范。
3. **注册 (Register)**: 分配 URN，写入注册表。
4. **废弃 (Deprecate)**: 标记为 deprecated，保留向后兼容。
5. **移除 (Remove)**: 在下一个 MAJOR 版本中移除。

### 5.3 完整扩展示例：新增蓝碳计量原子 BlueCarbonAccountingAtom

#### 需求

海岸带蓝碳计量需要记录碳通量、碳储量和碳交易属性，核心 schema 无此原子。

#### XSD 扩展片段

新增文件 `extensions/blue-carbon.xsd`:
```xml
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema"
           xmlns:cz="http://cz-dsl.org/schema/1.0"
           xmlns:bc="http://cz-dsl.org/schema/1.0/ext/blue-carbon"
           targetNamespace="http://cz-dsl.org/schema/1.0/ext/blue-carbon">

  <xs:import namespace="http://cz-dsl.org/schema/1.0"
             schemaLocation="cz-dsl.xsd"/>

  <!-- 蓝碳计量原子，继承 AtomType -->
  <xs:complexType name="BlueCarbonAccountingAtomType">
    <xs:complexContent>
      <xs:extension base="cz:AtomType">
        <xs:sequence>
          <xs:element name="CarbonFlux" type="xs:double"/>
          <xs:element name="CarbonStock" type="xs:double"/>
          <xs:element name="HabitatType" type="xs:string"/>
          <xs:element name="Unit" type="cz:UnitType"/>
        </xs:sequence>
      </xs:extension>
    </xs:complexContent>
  </xs:complexType>

  <xs:element name="BlueCarbonAccounting"
              type="bc:BlueCarbonAccountingAtomType"
              substitutionGroup="cz:ExtensionSlot"/>
</xs:schema>
```

### 5.4 论证：扩展不需修改核心 schema

上述蓝碳计量扩展的完整实现仅涉及：

1. **新建** 扩展 schema 文件（`extensions/blue-carbon.xsd`、
   `extensions/blue-carbon.schema.json`）。
2. 在实例中使用 `ExtensionSlot`（XML）或 `x-` 前缀属性（JSON）插入扩展内容。
3. 在扩展注册表中登记。

**核心 schema `cz-dsl.xsd` / `cz-dsl.schema.json` 未被修改**。这是因为：

- `AtomType` 的 `xs:anyAttribute processContents="lax"` 允许任意附加属性。
- `ExtensionSlotType` 的 `xs:any processContents="lax"` 允许任意子元素。
- JSON Schema 的 `patternProperties: {"^x-": {}}` 允许任意 `x-` 前缀属性。
- `substitutionGroup="cz:ExtensionSlot"` 允许扩展元素替换扩展槽位置。

因此，协议满足**开放-封闭原则**：对扩展开放，对修改封闭。

## 6. 互操作映射表

### 6.1 与 KML/CityGML/GML 互操作

| CZ-DSL 概念 | KML 对应 | CityGML 对应 | GML 对应 |
|----------------|----------|-------------|----------|
| CZScenario | Document | CityModel | FeatureCollection |
| CoordinateReference | Region/LatLonAltBox | CRS (gml:SRS) | gml:Envelope+srsName |
| SpatialReference (Point3D) | Point/Coordinates | gml:Point | gml:Point |
| ClassificationLayer | Folder/Document | CityObjectGroup | gml:featureMember |
| PhysicalAsset | Placemark | Bridge/Building/Tunnel | AbstractFeature |
| TemporalReference | TimeSpan/TimeStamp | validity | gml:validTime |
| DataSource | NetworkLink | appearance/texture | observationProvider |
| ExtensionSlot | ExtendedData/Schema | generics | _GenericApplicationPropertyOf* |

**映射策略**:
- **导出为 KML**: 将 `PhysicalAsset` 映射为 `Placemark`，`ClassificationLayer` 映射
  为 `Folder` 层次，扩展数据写入 `ExtendedData`。
- **导入 CityGML**: 将 `CityObjectGroup` 映射为 `ClassificationLayer`，建筑/桥梁/
  隧道映射为 `PhysicalAsset`，通用属性映射到 `ExtensionSlot`。
- **GML 互操作**: 所有几何对象通过 GML 语法交换，`srsName` 映射到
  `CoordinateReference` 的 EPSG 或 WKT。

### 6.2 与 SEDRIS / CDB 互操作

| CZ-DSL 概念 | SEDRIS SRM 对应 | SEDRIS EDCS 对应 | CDB 对应 |
|----------------|-----------------|------------------|----------|
| CoordinateReference | SRM SRF (Spatial Reference Frame) | — | CDB Coordinate System |
| ClassificationLayer | — | EDCS Classification Code (ECC) | CDB Dataset Code (Dxxx) |
| TemporalReference | SRM temporal | EDCS Time | CDB Time Step |
| DataSource | DRM Transmittal Root | EDCS Attribute Value | CDB Tile |
| PhysicalAsset | DRM Feature Geometry | EDCS Object | CDB Model |
| UncertaintyModel | DRM uncertainty | EDCS uncertainty | CDB LOD |
| ResolutionSpec | DRM resolution | EDCS resolution | CDB LOD Level |
| ExtensionSlot | DRM Property | EDCS Custom Attribute | CDB Extended Dataset |

**映射策略**:
- **导出为 SEDRIS STF**: `CoordinateReference` 映射到 SRM SRF（如
  `SRM_GEODETIC_WGS_1984`），`ClassificationLayer` 的 `edcsRef` 映射到 EDCS ECC。
- **导入 CDB**: CDB 瓦片目录（`Dxxx_Sxxx_Txxx`）映射为 `DataSource`，LOD 级别映射
  为 `ResolutionSpec`。

## 7. 版本演进与生命周期策略

### 7.1 语义化版本

CZ-DSL 采用语义化版本（Semantic Versioning）：

| 版本变化 | 含义 | 兼容性 |
|----------|------|--------|
| MAJOR (x.0.0) | 不兼容的架构变更 | 需迁移指南 |
| MINOR (2.x.0) | 新增组件/原子 | 向后兼容 |
| PATCH (2.0.x) | Bug 修复与文档更新 | 完全兼容 |

### 7.2 弃用流程

1. **公告 (Announce)**: 在发布说明中标记为 `@deprecated`，提供替代方案。
2. **宽限期 (Grace Period)**: 至少保留 2 个 MINOR 版本的兼容支持。
3. **移除 (Remove)**: 在下一个 MAJOR 版本中移除。

示例弃用标注:
```xml
<xs:element name="LegacyDataSource" type="cz:DataSourceType" deprecated="true">
  <xs:annotation>
    <xs:documentation xml:lang="zh">
      @deprecated 自后续版本起，请使用 DataSource 原子替代。
    </xs:documentation>
  </xs:annotation>
</xs:element>
```

### 7.3 迁移指南 (复合构造 → 原子构造)

#### 步骤 1：文本语法迁移

复合构造的 `.cz` 文件可直接被编译器前端解析。编译器在 AST 层面自动将 复合关键字
映射到 原子组件（参见 1.3 节映射表）。

#### 步骤 2：序列化格式选择

- **保留文本**: 适合人类编写和版本管理（Git diff 友好）。
- **转换为 XML**: 适合企业 SOA 架构与 XML 工具链集成。
- **转换为 JSON**: 适合 Web API 与微服务架构。

#### 步骤 3：分类编码迁移

自由文本分类需映射到四级编码体系：

```
v1: classification SaltMarsh extends EDCS_Tidal_Wetland
1.0: ClassificationLayer {
       level: CorePatch,
       code: "CZ.CP.SALT-MARSH",
       edcsRef: "ECC_SALT_MARSH"
     }
```

#### 步骤 4：坐标参考迁移

`spatial_reference_system` 块需映射到 `CoordinateReference` 类型，
补充 EPSG 代码或 WKT 定义。

#### 步骤 5：扩展迁移

通过约定（非标准）实现的扩展属性，应迁移到 `ExtensionSlot`（XML）或
`x-` 前缀属性（JSON），并在扩展注册表中登记。

### 7.4 生命周期状态

| 状态 | 含义 | 支持 |
|------|------|------|
| Experimental | 实验性，可能随时变更 | 社区反馈 |
| Draft | 草案，公开征求意见 | 有限 |
| Stable | 稳定发布 | 完整支持 |
| Deprecated | 已弃用，即将移除 | 仅安全修复 |
| Retired | 已退役，不再支持 | 无 |
